# 人間承認の本人確認（Security Fix 001 と今後の設計）

## 問題（修正前）

- `aiwos.py transition --to accepted --by human` は、`--by` に書かれた文字列をそのまま人間の意思として記録していた。
- `validate-task.py` は `history[].by == "human"` という文字列だけで最終承認を有効としていた。
- `reviewer: human` のタスクは、`produced_by: "human"` と書かれた `review_note` が1件あれば人間レビュー済みとされていた。

AI・スクリプト・自動化プロセスは誰でもこの文字列を書けるため、人間を名乗って最終承認やレビューを偽装できた。

## 現在の挙動（フェイルクローズ）

本人確認の仕組みはまだ実装されていない。実装されていないものを実装済みとして扱わないため、
**人間の本人確認が必要な操作はすべて拒否する。**

| 操作 | 修正後 |
|---|---|
| `aiwos.py transition --to accepted --by <誰でも>` | 拒否（終了コード 3）。契約は変更しない |
| 契約 JSON を手で編集して `accepted` にする | `validate-task.py` が不正と判定（`check.sh` も失敗） |
| `reviewer: human` のタスクを `passed` にする | 不正と判定（人間レビューを検証できない） |
| その他の手動遷移（中断・再開・取り消しなど） | 実行できるが、履歴の `note` に「CLI で宣言された実行者で、未検証」と記録する |

`passed` の判定（3軸 PASS・証拠ハッシュ・実行記録による独立性）は変更していない。
`passed` は品質ゲートの通過であり、人間の承認ではない。

## 今後の設計案：GitHub の認証済み承認と連携する

GitHub は操作者を認証している。そこで、最終承認を「GitHub 上で認証された人間の Pull Request 承認」として
表現し、ランナーはその事実を GitHub から取得して照合する。

### 流れ

1. タスクが `passed` になったら、`passed → accepted` の変更だけを含む PR を作る（承認 PR）。
2. 承認者は GitHub 上でその PR に **Approve** のレビューを付ける。この操作は承認者本人のログインセッションでしか行えない。
3. 検証コマンド（例: `aiwos.py verify-approval TASK --pr N`）が GitHub API から次を取得し、すべて満たす場合だけ `accepted` を有効とする:
   - レビューの状態が `APPROVED`、`commit_id` が承認 PR の最新コミットと一致
   - レビュアーが承認者リスト（例: `core/approvers.json`、または CODEOWNERS）に含まれる
   - レビュアーが PR の作成者・コミット作成者と異なり、Bot アカウントではない
   - 承認 PR の差分が対象タスクの `status` / `history` / `approval` 以外を変更していない
4. 取得した事実（PR 番号、レビュー ID、レビュアーのログイン名、`commit_id`、取得時刻、API 応答の SHA-256）を
   契約の `approval` 証拠として記録する。`validate-task.py` は、この証拠がない `accepted` を引き続き拒否する。

### リポジトリ側で必要な設定

- main のブランチ保護: PR 必須、承認 1 件以上、CODEOWNERS のレビュー必須、承認後の push で承認を無効化
- `CODEOWNERS` で `examples/**/task.json` などの契約ファイルの所有者を人間に限定
- AI が使う GitHub トークンにはレビュー承認の権限を与えない。ランナーは子プロセスに `GH_TOKEN` を渡さない（実装済み）

### この設計でも残るリスク

- 承認者本人のトークンや GitHub セッションを AI が使える環境では、AI が本人として承認できる。
  承認者の認証情報を AI の実行環境に置かないことが前提になる。
- 検証はオンライン（GitHub API）で行う必要がある。オフラインで検証したい場合は、承認者の署名付きコミット
  （SSH/GPG 署名と `allowed_signers` ファイル）による代替案がある。
- ブランチ保護を変更できる管理者権限は、この仕組みの外にある。

### 未実装

上記の検証コマンド、`approval` 証拠の形式、承認者リスト、ブランチ保護の設定はいずれも **未実装**。
実装されるまで `accepted` には到達できない。
