# PROFILE: development（システム開発）

ソフトウェアの変更（機能追加・不具合修正・リファクタリング）を扱う。
共通OS（`core/`）の規則はすべて適用され、ここでは業務固有の部分だけを定める。

## 入力

- 変更対象のファイル・ディレクトリ（`kind: file`、リポジトリ相対パス）
- 既存テスト、Issue、仕様書
- 社外秘のコード・データは `kind: reference` で場所だけを示し、リポジトリに入れない

## 受入基準の書き方

| 品質軸 | 典型的な基準 | 検証方法 |
|---|---|---|
| spec_conformance | 要求された入出力・挙動になっている | `command`（受入テスト） |
| correctness | 既存テスト + 追加テストが通る、lint/型検査が通る | `command` |
| completeness | テスト追加・ドキュメント更新・エラー処理 | `inspection`（レビュアーが確認） |

- 「動くこと」は必ずコマンドで検証できる形にする。
- テストを削除・skip・期待値の書き換えで通すことは失敗条件として明記する。

## 既定の失敗条件

- 既存テストの失敗 → `rework`
- 制約外のファイル変更 → `escalate`
- テストの削除・無効化 → `escalate`
- 秘密情報のコミット → `escalate`

## 証拠

- テスト・lint のコマンドと終了コード（`command_output`）
- 変更差分（`diff`）
- レビュアーの所見（`review_note`）

## 役割の目安

- 実装: Claude Code または Codex CLI
- レビュー: 実装しなかった方。重要変更は人間が最終判断する。
