| 1 | 無限再試行 | `claim()` は `attempts` を見ない。`reclaim()` だけが上限を見るが、対象はリース中のタスクのみ。ワーカー内の例外・タイムアウトで `queued` に戻ったタスクは 60 秒ごとに無制限に再取得される。**加えて**、例外の経路ではモデルが起動済みでも AI 実行回数に数えていなかった |

| 試験 | 確認内容 |
|---|---|
| `RetryLimitStore`（work/check/review/judge） | 例外による再試行は `max_stage_attempts`=3 回で止まり、held になる（理由に試行回数） |
| `RetryLimitIntegration` × 4（work/check/review/judge） | 実際のワーカー内例外（git の commit-msg フックで commit を拒否）が起きると、`max_stage_attempts=1` で直ちに held。取得は 1 回だけ。モデルを起動した段階は AI 実行回数に数える（work 失敗で 1、review/judge 失敗で 2） |
| `PullRequestRetry` | push はすべて成功し、PR 作成だけが失敗し続けた状態から、GitHub の回復後に同期が PR 作成だけを再試行して 1 件作成。その後の同期でも重複しない |
| `LiveOwnerExpiredLease` | ワーカーを SIGSTOP で凍結すると、リース期限切れ後に controller がそのワーカーと子プロセスを停止し、消滅を確認してから回収する。エージェントの実行は 1 件のみ（並走しない） |
| `GitHubStateSync` × 4 | ① escalated のタスクを人がタスクブランチで ready に戻すと取り込んで再開し、人の commit の上に積む ② 作業前に main の契約を変える（担当変更）と取り込む ③ 作業開始後に main の契約を変えると held ④ ローカルとリモートが分岐すると held になり、どちらの commit も上書きしない |

## 修正中に追加した対策（修正 3 の副作用への対処）

リース更新を別スレッド（`LeaseKeeper`）に移したため、本体スレッドがタイムアウトの無い処理で止まっても
リースが更新され続ける、という新しい穴ができた。`LeaseKeeper` は「段階のタイムアウト + 猶予 + git 操作の許容時間
（1200 秒）」を過ぎると更新をやめる。止まったワーカーのリースはその後期限切れになり、controller が停止・回収する。
回帰テスト `LeaseKeeperLimit` を追加した（修正前のコードには `LeaseKeeper` 自体が無いため、修正前の失敗は示せない）。

## 残存リスク

- held の解除は GitHub への push（タスクブランチ、または作業前の main）だけで行う。controller に held を解除するコマンドは無い
- 作業開始後に main の契約が変わったタスクは held のまま。人がタスクブランチ側の契約を更新して push する必要がある
- SIGKILL でも消えないプロセスが残ると、そのタスクは回収されない（安全側に止まる）。再現できておらず未検証
- 本体スレッドが止まったワーカーは、`LeaseKeeper` の更新期限（段階の上限 + 1200 秒、既定の work では約 35 分）を
  過ぎるまで検出されない。その間、そのタスクは進まない（二重実行は起きない）
- 実際の GitHub API（`gh pr create` の失敗の仕方）、実際の systemd、長時間運転は引き続き未検証
